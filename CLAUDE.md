# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository Layout

Four sibling projects forming one AI-powered Playwright testing suite. They share no code — the Extension talks to the Bridge over WebSocket; the Orchestrator is fully standalone.

| Project | What it is | Runtime |
|---|---|---|
| `PlaywrightExtension/` | "Playwright AI Studio" Chrome MV3 extension (side panel UI, AI agents) | Browser, no build step |
| `PlaywrightBridge/` | Local WebSocket server the extension uses for real Playwright runs + Claude Code CLI as LLM | Node (ESM) |
| `PlaywrightOrchestrator/` | Standalone multi-agent QA CLI (`pworch`), 15 TypeScript agents | Node + ts-node |
| `PlaywrightPlatform/` | Test-management backend (Fastify + PostgreSQL) and React web app; the extension signs in to it over HTTP, and it runs stored scripts on Jenkins | Node + Docker |

`PlaywrightOrchestrator/CLAUDE.md` has full detail for that project — read it before working there.

Feature design docs live in `docs/superpowers/specs/` (one dated markdown file per feature) — check for an existing spec before designing changes to the Extension panels.

## Commands

### PlaywrightBridge
```bash
cd PlaywrightBridge
npm run setup        # npm install + npx playwright install chromium (once)
npm start            # WebSocket server on ws://127.0.0.1:8787
```
No tests/lint of its own — `tests/bridge.spec.ts` is a scratch file overwritten on every `runCode` request from the extension.

### PlaywrightExtension
No build, no package.json — plain ES modules loaded by Chrome. Load via `chrome://extensions` → Developer mode → "Load unpacked" → select `PlaywrightExtension/`. After editing, click the reload icon on the extension card (service-worker + side panel changes need it).

### PlaywrightOrchestrator
```bash
cd PlaywrightOrchestrator
npm run dev                  # CLI help via ts-node
npm run build                # tsc → dist/
npx tsc --noEmit             # typecheck
npm test                     # playwright test (all 5 browser projects)
npx playwright test tests/examples/sample.spec.ts --project=chromium   # single test
```
See `PlaywrightOrchestrator/CLAUDE.md` for the full CLI command list (plan/generate/execute/heal/orchestrate/...) and architecture.

### PlaywrightPlatform
```bash
cd PlaywrightPlatform
docker compose up -d postgres && npm run db:migrate && npm run db:seed   # once
npm run dev:server           # API on :3000
npm run dev:web              # web on :5173
npm test                     # server tests (Vitest, real Postgres)
npm run test:e2e             # web tests (Playwright)
npm run typecheck
```
Layering is strict: `routes/` → `services/` → `repositories/`; only repositories query the database; only `web/src/api/` calls `fetch` in the web app; only `server/src/jenkins/jenkins-client.ts` calls Jenkins. Server tests use a local stand-in for Jenkins (`server/test/jenkins-stub.ts`). See `PlaywrightPlatform/README.md`.

The Jenkins job is generated by `server/src/jenkins/pipeline.ts` and pushed by Settings → Jenkins → **Create Job** (press it again after changing that file or `PLAYWRIGHT_DOCKER_IMAGE`). A build runs `npm install` and `npx playwright test` inside the official Playwright Docker image with `docker run` from the agent's shell — never the Docker Pipeline plugin — on Windows or Linux agents (`isUnix()` picks `bat` or `sh`); the agent needs only Docker and `curl`. `@playwright/test` is pinned to the version in the image tag (`playwrightVersionFromTag`). Only the agent talks to the platform: it downloads the script and posts `result-body.json`; no `docker run` line may carry `RUN_TOKEN` or `PLATFORM_URL` (pinned by `server/test/jenkins-client.test.ts`).

## Architecture

### Extension (PlaywrightExtension)
- **`sidepanel.js`** is the hub: instantiates the `Orchestrator` (agents/orchestrator.js) with the selected AI provider and wires all panel UI. `sidepanel.html`/`sidepanel.css` hold the entire UI.
- **Agents** (`agents/`): planner, generator, healer, recorder, inspector, chat, framework, export, session — all extend `BaseAgent` (`agents/base-agent.js`) and receive an `AIProvider`. Official Playwright test-agents flow: planner → generator → healer (`Orchestrator.runFullPipeline`).
- **Templates** (`templates/`): `test_plan_template.md` and `test_case_template.md` are the source of truth for test-plan output structure — the planner agent fetches them at runtime and embeds them in its system prompt. Change the plan format by editing the templates, not the agent prompt.
- **Providers** (`providers/`): implement `AIProvider.complete({system, prompt})` (`base-provider.js`). `mock` is default (no key, canned output, 15KB of realistic samples), `claude`/`openai`/`gemini` call public APIs with a user-supplied key, `bridge` proxies to the local Claude Code CLI via the Bridge. Provider switching lives in `sidepanel.js` `updateProvider()`; settings persist through `utils/storage.js` (chrome.storage).
- **`background.js`** (MV3 service worker): message relay only — injects/reaches `content.js` in the active tab (`RELAY_TO_CONTENT`), exposes tab info and debugger-based network capture. `content.js` does in-page work: recorder event capture and element inspection.
- **Recorder pipeline**: `content.js` captures DOM events (a `navigate` action with the current URL is recorded on start, so generated tests begin with `page.goto`) → streams `RECORDING_ACTION` messages to the side panel → `utils/playwright-codegen.js` `actionsToTest()` renders code (`normalizeActions()` collapses per-keystroke `fill` events to the final value and drops clicks on `<html>`/`<body>`). `getBestLocatorText()` in `content.js` must emit valid Playwright selector-engine syntax (`text="..."`, CSS attribute selectors) — its output lands verbatim inside `page.locator('...')`, and it is also the identity `normalizeActions()` compares steps by. Text comes from `innerText` (`textContent` includes `<script>` source). Raise `VERSION` in `content.js` with every change to it: a page keeps the script it was given before the extension was reloaded.
- **Recorder locators** (`locatorsFor()` → `getElementInfo()` in `content.js`): every candidate carries `matches`, the number of elements it finds, and one that finds exactly one always wins. Order by score: a test attribute (`data-testid` → `getByTestId`, then `data-test`/`data-cy`/`data-qa`/`data-automation-id`), `getByRole` with a name, `getByLabel`, `getByPlaceholder`, `getByText`, `getByAltText`, `getByTitle`, id, a link's `href`, `name`, a role with no name. Text with a 3+ digit number in it is treated as data and scored down (`steady()`). When nothing is unique, `scopedLocator()` names the part of the page first (`CONTAINERS`: row, list item, dialog, named region, table…) — `getByRole('row').filter({ hasText: 'Ada' }).getByRole('button', { name: 'Delete' })`, with one more level (`locator('#table1').getByRole('row')…`) when rows repeat across tables; then `.first()`/`.nth(n)`; then `cssFor()`, a short class selector, with the `nth-of-type` path (`cssPath()`) as the very last resort. `roleOf()` and `accessibleName()` must agree with Playwright's own reading (a password or date `<input>` is a `textbox`; a row has no name from its content) — a mismatch gives a locator that finds nothing or, with `.nth()`, the wrong element. Queries go through `deepAll()`, which looks inside open shadow trees in page order.
- **What is a recorded step**: a click lands on the nearest `ACTIONABLE` ancestor, never on `<html>`/`<body>`. A click on something not made to be clicked (`isClickable()` false: no control, interactive role, handler attribute, pointer cursor, or own short text) is held for 700 ms (`holdClick()`) and kept only when the page then shows something new or is left. A hover is recorded only when it opens something, and only on an element made to be pointed at when the cause is a page change. `normalizeActions()` drops the click before a `fill` of the same field, a hover the next step makes redundant, and a hover followed by nothing or by leaving the page. `STOP_RECORDING` records an `end` action that carries the final address.
- **Frames, dialogs, new tabs**: `content.js` runs in every frame (`all_frames`); only the top frame (`isTop`) shows the monitor, answers the side panel, and records navigation, while a frame prefixes its steps with `framePrefix()` (`frameLocator('#pay-frame').`). `page-hooks.js` runs in the page's own world (`"world": "MAIN"`) and reports `alert`/`confirm`/`prompt` and their answers by `postMessage`; it wraps those three functions on every page while the extension is enabled. `background.js` announces a tab opened from another (`TAB_OPENED`), and `sidepanel.js` tags that tab's steps with `page: n` (`recorderPopups`).
- **Recorder code** (`stepLines()` in `utils/playwright-codegen.js`): `page.once('dialog', …)` and `const page1Promise = page.waitForEvent('popup')` go before the step that causes them; steps in a new tab use `page1.`; `await expect(page).toHaveURL(/…/)` follows a step after which the address differs, and replaces `page.goto` for a route change inside a single-page app (any `navigate` after the first).
- **Two run paths**, shared by the Generator and Recorder panels via helpers in `sidepanel.js` (`runCodeViaBridge`, `runCodeLive`): Bridge = real `npx playwright test` (headed) with streamed output; Live = `utils/test-runner.js` parses the generated code line-by-line and replays steps on the active tab, with failed steps routable to the Healer panel. The Live parser reads a string up to the quote it opened with (`'[data-test="x"]'` is one string) — keep it that way, with `tests/test-runner.test.mjs`. `resolveLocator()` in `content.js` is the Live runner's locator engine: it understands `text=` selectors, every `getBy*` the recorder writes, chains (`locator.then`), `.filter({ hasText })`, and `.first()`/`.nth()`/`.last()` (`locator.pick`); a step that finds no element is retried for 5 seconds, and `toHaveURL` takes a string or a `/regex/`. Lines it cannot do in the page — `frameLocator`, `waitForEvent('popup')`, `page1.` steps, `page.once('dialog')` — are shown as skipped, "Run via Playwright only". Bridge runs go through `runUntilPassing()` (`utils/heal-run.js`): a failed run is healed and run again, twice at most, and the code that passed is written back to the code box (`onPassed`). The Generator heals with the chosen AI provider first and the Playwright healer agent second; the Recorder passes `agentFirst`, so the agent (`BridgeClient.agentHeal`, needs `PlaywrightBridge/.claude/agents` and `.mcp.json`) fixes every time. AI Enhance (`RecorderAgent.run`) tidies the code in the box when it was edited, healed, or passed, keeps that code when the model returns no test, and is refused on the mock provider.
- **Checking the recorder**: unit tests cover the codegen and the Live parser only (`node --test "PlaywrightExtension/tests/*.test.mjs"`). A change to locator choice in `content.js` must be checked against the real engine: inject `content.js` into a page with a stubbed `chrome.runtime`, take each element's first locator, and assert that real Playwright finds exactly one element with it, and the same one.
- **`utils/bridge-client.js`**: WebSocket client for the Bridge (`ws://127.0.0.1:8787`), used for `runCode` (real test runs, streamed output) and `complete` (LLM via Claude Code CLI).
- **Platform link** (`utils/platform-client.js`, `utils/code-extract.js`, `utils/execution-view.js`): optional sign-in to the Playwright Platform (Settings → Platform, `setupPlatform()` in `sidepanel.js`), the "💾 Save to Project" buttons in the Generator, Recorder, and Orchestrator panels (`setupSaveToProject()`), the **Projects** tab that browses stored scripts and runs them on Jenkins (`setupProjectsPanel()`), and the Jenkins connection form under Settings (`setupJenkinsSettings()`, ADMIN only). The extension never calls Jenkins: every request goes to the platform API through `platform-client.js`. The three `utils/` modules are free of DOM and `chrome.*` calls and are tested with `node --test "PlaywrightExtension/tests/*.test.mjs"`; decisions such as which buttons show and which links are safe live there, not in `sidepanel.js`. Text that came from the server is always written with `textContent`. The extension works unchanged when not signed in.

### Platform runs and reports (PlaywrightPlatform)
- **The Jenkins job** is generated by `server/src/jenkins/pipeline.ts` (`pipelineScript()`, with the build's `package.json`, `playwright.config.ts`, and result-reporting script as strings) and pushed to Jenkins by Settings → Jenkins → **Create Job**. After changing that file, press Create Job again: Jenkins keeps the old definition until then. `agent any`; the tests run headless Chromium inside the Playwright Docker image on the agent (no grid, no hub) — see the Docker paragraph under Commands → PlaywrightPlatform.
- **Two reports per build**, both archived: the Playwright HTML report (`playwright-report/`) and an Allure report (`allure-report/index.html`, one file, made by `allure-playwright` + `npx allure awesome --single-file`, Allure 3, no Java; generated inside the Test container, because the agent has no Node.js).
- **Reports are never linked to Jenkins directly.** Jenkins serves archived HTML with scripts switched off (`Content-Security-Policy: sandbox; default-src 'none'`), which leaves both reports blank. Instead: `GET /api/executions/:id/reports` (signed in) answers `{ reports: { playwright, allure } }`, each a path or null; `GET /api/reports/:token/:kind/*` serves the files, fetched from Jenkins with the platform's credentials. That route has no session guard: the token is an HMAC-signed link (`server/src/security/report-links.ts`) that names the run and expires after an hour, because a report opens in its own tab where the extension cannot send its bearer token.
- **A report is untrusted HTML** (a test script produces it), so that route answers with `Content-Security-Policy: sandbox allow-scripts allow-popups allow-downloads` — scripts run, but with no origin, cookies, or storage of the platform. Do not add `allow-same-origin`. Both viewers read `localStorage` on start, so `execution-service.ts` injects an in-memory stand-in (`STORAGE_SHIM`) into served HTML; `Cross-Origin-Resource-Policy: cross-origin` lets the sandboxed page load its own images. The trace viewer inside the Playwright report needs a service worker and does not work this way.
- **The run report page**: `GET /api/reports/:token/` renders `server/src/reports/run-report-page.ts` — the script, version, run, who and when, each test's result, and both reports framed as two tabs. It is plain HTML and CSS with no script and every value escaped; keep it that way (its policy is `default-src 'none'`). The build is told what to call the run through the job parameter `RUN_LABEL`, set in `ExecutionService.start` and written to `run-label.txt` by Jenkins itself, never put on a command line; both report configs read it. `SCREENSHOTS` and `VIDEO` (`on`/`off`) reach the build the same way, as two booleans in `run-options.json`.
- **One run may hold several scripts.** `POST /api/projects/:id/run` with `{ scriptIds }` starts ONE run — one Jenkins build, one report — of scripts ticked together; `POST /api/scripts/:id/run` is the same path with one script (`ExecutionService.start`). The scripts of a run are rows of `execution_scripts`; `test_executions.script_id` is the first of them. The build fetches them all with `GET /api/executions/:id/scripts` (run token) as `{ files: [{ name, content }] }` into `scripts.json`, and `unpack-scripts.cjs` writes them into `tests/` inside the container, accepting only plain `*.spec.ts` names. File names come from `specFiles()` in `pipeline.ts`; each reported test carries its file, which is how a result gets its `script_id` and how each script is marked passed or failed by its own tests. A script counts as running while any run that contains it is unfinished.
- **Projects tab** (`setupProjectsPanel()`): add, rename, and delete a project (ADMIN); edit a script's name and text; tick scripts and run them together as one run (`PlatformClient.runScripts`), or delete the ticked ones; choose screenshots and video before a run. Who sees which control is decided in `utils/execution-view.js` (`manageControls`, `runControls`, `deleteControls`).
- **Where they show**: `web/src/pages/ScriptRuns.tsx` (Recent runs table on the script page) and the extension's run card (`reportLinks()` in `utils/execution-view.js`, `getReportLinks()` in `utils/platform-client.js`).

### Bridge (PlaywrightBridge)
Single file, `server.js`. Protocol: JSON `{id, cmd, payload}` messages — `ping`, `runCode` (writes `tests/bridge.spec.ts`, spawns `npx playwright test` headed, streams stdout), `complete` (pipes prompt to `claude -p`), `stop`. Binds 127.0.0.1 only — it executes arbitrary Playwright code and shells out to `claude`, so never expose the port.

### Orchestrator (PlaywrightOrchestrator)
Separate multi-agent framework — event bus + singleton registry + `OrchestratorAgent` routing `TaskType` → agent. Full architecture documented in its own CLAUDE.md.

## Cross-project Conventions

- The Extension's agent/provider names (planner, generator, healer...) mirror the Orchestrator's agents but the implementations are independent — a change in one does not affect the other.
- Bridge protocol changes must be kept in sync on both sides: `PlaywrightBridge/server.js` and `PlaywrightExtension/utils/bridge-client.js`.
- Platform API changes must be kept in sync on both sides: the routes in `PlaywrightPlatform/server/src/routes/` and `PlaywrightExtension/utils/platform-client.js`.
